# 統合版 コントローラー操作仕様（案）

MineTrigger Bedrock Edition — Switch Pro Controller Input Specification v0.1

このドキュメントはたたき台です。実機検証や仕様変更に応じて、このファイルを直接書き換えて確定させてください。

---

## 1. 前提として分かっていること（要点）

- Bedrock Script APIには「攻撃ボタンを押したが何にも当たらなかった（空振り）」を検知する専用イベントが存在しない
  - `entityHitEntity` / `entityHitBlock` は**命中確定時のみ**発火（＝ブロックや敵に当てた場合はZR/ZLどちらでも確実に検知できる）
  - `itemUse`（何もない方向）/ `itemUseOn`（ブロック方向）/ `playerInteractWithEntity`（エンティティ方向）は、**照準先に関係なくボタンを押した時点で必ずどれか1つが発火する**
  - → **「完全に何もない方向への空振り」だけは、ZR（Attack系）だと検知手段がない。** ZL（Use系）なら空振りでも検知できる。ブロック/敵への攻撃はZR/ZLどちらでも問題ない
- `InputButton`（`InputInfo.getButtonState` / `PlayerButtonInputAfterEvent`）で生の押下状態を取得できるボタンは **Jump と Sneak の2つだけ**。L/R・十字キーなど他のボタンは直接読めず、その機能が引き起こす**副産物（ホットバー選択変化など）を経由してしか間接的に観測できない**
- バニラのオフハンドスロットは**盾・トーテム・矢・地図のみ受付**という制限がある。カスタム武器アイテムをそのまま入れられるかは未検証（要プロトタイプ確認）
- 移動・スロット選択（ホットバー送り）は完全にバニラ動作のまま変更しない

## 3-2. インベントリ画面を開いている間の操作（案・実現性に強い疑義あり）

インベントリ画面中はボタンの意味をバニラ側も変えている（ZL/ZRが「アイテム移動」に、L/Rが「タブ切替」になる等）。これに合わせてMineTrigger側でも「カーソルで選択中のアイテムをZL/ZR/十字キーでそのまま各スロットに装備する」という案が出ているが、**現時点ではほぼ実現不可能と見ている**（詳細は4-6）。

| ボタン | バニラ機能（インベントリ中） | MineTrigger案（インベントリ中） | 実現性 |
|---|---|---|---|
| Lスティック | カーソル移動 | カーソル移動（変更なし） | ⭐ |
| Rスティック | スクロール | スクロール（変更なし） | ⭐ |
| Aボタン | アイテムを掴む/置く | 変更なし | ⭐ |
| Bボタン | インベントリを閉じる | 変更なし | ⭐ |
| Xボタン | アイテムを分ける | 変更なし | ⭐ |
| Yボタン | アイテムをクイック移動 | 変更なし | ⭐ |
| L / R | タブ切替 | 変更なし | ⭐ |
| ZL / ZR | 同種アイテムを一括移動 | 選択中アイテムを左手/右手武器として装備 | ❌ほぼ不可（4-6参照） |
| 十字キー4方向 | カーソル移動 | 選択中アイテムをオプショントリガー①〜④に装備 | ❌ほぼ不可（4-6参照） |

## 4. 未解決の論点（要決定）

### 4-1. 左手武器スロットをどう扱うか（解決済み）

バニラの「本物のオフハンドスロット」（プレイヤーアイコン横の盾アイコンの1マス）は盾・トーテム・矢・地図しか受け付けないハードコードされた制限があり、ここにカスタム武器を直接入れることはできない。

**→ そもそもこの専用スロットを使わない。** 4-6で採用する「スロット位置で判定」方式（案B）と統一し、**ホットバーの特定位置（例：スロット1）に置いた武器を「左手武器」として扱う**運用にする。ホットバーの通常スロットにはアイテム種別の制限が一切ないため、この方式ならカスタム武器を自由に左手武器として運用できる。バニラの専用オフハンドスロットは今回の設計では使用しない。

### 4-2. オプション武器（十字キー4方向）の扱い

十字キー4方向にオプショントリガーを割り振る案は、4-5の検証結果次第で実現性が変わる。検知できない方向が出た場合は、そのオプションだけホットバー統合に切り替える等の代替が必要。

### 4-3. ZR（右手武器）の空振り検知をどう補うか

- **案A**：右手武器は近接武器を割り当てない運用ルールにする（ブロック/敵への攻撃は検知できるため、遠距離武器主体なら実用上問題が起きにくい）
- **案B**：右手武器も左手側と同様、ZRではなくZL系イベントに相乗りさせる（＝ZRとZLどちらを押しても「今選択中の手」の武器が出る、という設計に寄せる。ボタンと手の対応という直感的UXは失われる）
- **案C**：完全な空振りをトリオン消費なしの許容仕様として受け入れる（判定を妥協する）

### 4-4. L/R・Bボタンの間接検知が実際に機能するか

L/R（特殊技）、B（ジャンプ転用）は、いずれもバニラ機能の副産物（ホットバー選択変化、ドロップイベント等）を検知して代用する前提。この間接検知が体感できるラグなく機能するかは実機プロトタイプでの検証が必須。

### 4-5. 十字キーの押下がサーバー側で検知可能か

視点切替・エモートメニューはクライアントローカルな処理である可能性があり、その場合サーバー側スクリプトには**何のイベントも届かない**。この場合、十字キーをオプショントリガーに使う案自体が成立しない。最優先で検証すべき項目。

### 4-6. インベントリ画面中のZL/ZR/十字キー装備割り当てが技術的に厳しい

調査の結果、以下2点がAPIとして見当たらなかった。

- インベントリ画面でコントローラーのカーソルが**今どのスロットをホバーしているか**を取得する手段（`Container`/`ContainerSlot`はスクリプト側から中身を読み書きするAPIであり、UIのカーソル位置とは無関係。`player.selectedSlotIndex`はホットバー選択スロットのみを指し、開いた画面内のカーソルとは別物）
- インベントリ画面が開いている間だけ**ZL/ZR/十字キーの挙動を差し替える**手段

これはJava版で`MixinInventoryScreen`/`MixinPlayerScreenHandler`を使って実現していた「バニラ画面そのものへの割り込み」と同種の要求であり、統合版には同等の仕組みが存在しない可能性が高い。3-2節の「ほぼ不可」の根拠。

代替案：

- **案A：独自フォームUI化**　`ActionFormData`/`ModalFormData`（確認済みAPI、ボタン選択を確実に取得可能）で専用の「装備変更」画面を作る。バニラのインベントリ画面とは別物になり、開いている間はゲームが一時停止する
- **案B：スロット位置だけで判定**（Java版方式に近い）　ホットバーの特定位置（例：スロット0＝右手、1＝左手、2〜5＝オプション①〜④）に武器を置くだけでロードアウトとして認識する。装備の入れ替えは無改造の標準ドラッグ&ドロップで行う。ボタン差し替えは一切不要なので最も確実

いずれの案にするかは要判断。案Bを基本としつつ、余裕があれば案Aで使い勝手を補う、という段階的な進め方もあり得る。

## 5. 保持アイテム × 対象タイプの分岐条件

「ZL/攻撃系イベントを全部横取りする」だけでは不十分で、**何を持っているか**と**何に向けているか**の組み合わせでハイジャックするかどうかを分けないと、チェスト/ドアが一切開けない・食事もできない状態になる。

### 5-1. 現行Java版で見つかった抜け穴

`InputHandler.java` の `UseBlockCallback` / `UseEntityCallback` / `UseItemCallback` は、`stack.getItem() instanceof WeaponItem` の判定を**行う前に**無条件で `ActionResult.FAIL` を返している（107〜127行目付近）。トリオンは常時全快維持だが（`TrionSystem.java:260-265`）、金リンゴ等バフ目的の食事や、チェスト/ドア/かまど等のオブジェクト操作は、武器を持っていなくても常にキャンセルされてしまっている。これは統合版設計にそのまま持ち込まず、Java版側も直したほうがよい既存の不具合。

### 5-2. 分岐マトリクス（案）

| 持っている物 | 対象：何もない(空振り) | 対象：通常ブロック(壁など) | 対象：インタラクティブオブジェクト（チェスト/ドア/かまど/クラフト台/ベッド等） | 対象：エンティティ |
|---|---|---|---|---|
| **武器（WeaponItem）** | ハイジャック→武器発動 | ハイジャック→武器発動 | ⚠️要決定（5-3参照） | ハイジャック→武器発動 |
| **食べ物/バフアイテム** | バニラ動作を素通し（何も起きない） | バニラ動作を素通し | バニラ動作を素通し | バニラ動作を素通し |
| **その他バニラアイテム/空手** | 何もしない | バニラ動作を素通し（設置等） | バニラ動作を素通し（開く/使う） | バニラ動作を素通し |

判定順序のイメージ：

```
if (mainHandItem instanceof WeaponItem) {
    cancel vanilla action
    fire weapon logic (hit判定は自前)
} else {
    pass through -> vanilla側の処理に任せる
}
```

### 5-3. 未決定：武器を持ったままオブジェクトを操作したい場合

武器（例：ハンドガン）を持ったままチェストを開けたい、というケースが起こり得る。選択肢：

- **案A**：武器保持中はオブジェクト操作を完全にブロックする。開けたければ非武器アイテム（空手等）に持ち替える必要がある（実装は最も単純）
- **案B**：スニーク+使用の組み合わせのときだけオブジェクト操作を通す（例：スニークしながらZLでチェストが開く、スニークなしZLは武器発動）。特殊技は現在L/Rボタン側に割り当てているため、この案でも競合しない
- **案C**：武器の`tryActivate`側で「対象がインタラクティブオブジェクトだった場合は武器発動をキャンセルしてバニラ動作に譲る」判定を入れる

## 6. 次のアクション

優先度が高い順（＝実現性を左右する根本的な検証から）。

1. **【最優先】十字キーの押下がサーバー側スクリプトに何らかの形で届くか検証**（4-5）。届かない場合はオプショントリガーの割り当て自体を再設計する必要がある
2. L/Rボタン・Bボタンの間接検知（ホットバー選択変化・ドロップイベント経由）が実用的なラグで動くか検証（4-4）
3. ZR（右手武器）の完全空振りが実際どの程度ゲームプレイに影響するか、実機でのプレイ感を見ながら4-3の対応方針を決める
4. オフハンドスロットへのカスタムアイテム強制セットが可能か検証（4-1 案C）
5. 5-3の分岐方針を決定する
6. 上記の結果を踏まえて本ドキュメントの「未確定」欄を確定させる
7. （別件）Java版 `InputHandler.java` の無条件FAIL問題を修正するか判断する
